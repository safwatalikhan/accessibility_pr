## Pull Request Sampling Strategy

From a manually curated dataset of 300 accessibility-related pull requests, we selected a sample of 25 PRs for detailed analysis and repair evaluation. Each PR in our dataset could be associated with multiple broader issue types and multiple affected user demographics, while each PR belonged to a single application. Because of this multi-label structure, simple random sampling is not suitable for our goal. A random sample could overrepresent frequent issue categories while missing less common but technically important accessibility problems. Therefore, we used a coverage-based sampling strategy that prioritized coverage across broader issue types and user demographics while controlling the number and setup difficulty of applications included in the final sample.

Our primary sampling objective is to maximize broader issue type coverage so we can capture a broad range of accessibility repair tasks. Different accessibility issue types often require different repair actions, such as adding missing labels, correcting focus behavior, improving keyboard navigation, or adjusting visual presentation. Prioritizing broader issue type coverage helps ensure that the selected PRs represent a wide range of repair scenarios rather than many examples of the same kind of accessibility fix.

Our secondary objective is to maximize affected user demographic coverage. Accessibility issues can affect different groups of users, including users with visual impairments, users with motor impairments, users with cognitive impairments, and users who rely on assistive technologies. Since our study evaluates accessibility program repair, it is important that the sampled PRs reflect different user demographics. Therefore, after broader issue type coverage, we prioritize PRs that introduce previously uncovered user demographic labels.

Our third objective is to control the number of distinct applications required for evaluation. We require the final sample to include at least 10 distinct applications, while still trying to avoid unnecessary application setup overhead. This decision is motivated by the practical cost of conducting repair experiments on real-world applications. Each additional application requires separate setup effort, including cloning the project, installing dependencies, configuring the build environment, reproducing the issue, applying generated patches, and validating the repair. Since our primary goal is to evaluate accessibility repair behavior across issue categories rather than application-level variation, we treat the number of applications as an experimental cost while still requiring a minimum level of application coverage.

In addition to controlling the number of applications, we also account for application setup difficulty. We maintain an `app_flags.json` file that assigns each application a setup risk level. The risk levels, ordered from easiest to hardest, are `safe`, `yellow`, `red`, and `dark_red`. During sampling, the algorithm first attempts to satisfy the target sample size, broader issue type coverage, user demographic coverage, and minimum application count using only `safe` applications. If full coverage is not possible using only `safe` applications, the candidate pool is expanded to include `yellow` applications, then `red` applications, and finally `dark_red` applications if necessary. Applications not found in the risk file are treated as `dark_red` by default, so unknown setup difficulty is handled conservatively.

The sampling algorithm processes each eligible PR and extracts three fields: the set of broader issue types, the set of affected user demographics, and the application name. Since broader issue type and user demographic are multi-label fields, comma-separated values are split and normalized by removing extra whitespace. PRs with missing broader issue type or user demographic annotations are excluded from the sampling process because they cannot reliably contribute to the coverage objectives. We also maintain an explicit exclusion list for applications that are known to be infeasible or problematic for the current experiment.

Within each risk-level candidate pool, the algorithm maintains three sets representing the broader issue types, user demographics, and applications already included in the sample. For each candidate PR, the algorithm checks whether it introduces at least one previously uncovered broader issue type or user demographic. PRs that contribute new issue or user coverage are prioritized for selection. Application count is handled as a constraint: when possible, the algorithm prefers PRs from applications already represented in the sample, while also reserving enough remaining sample slots to reach the minimum of 10 applications.

After the coverage-driven selection step, if the sample contains fewer than 25 PRs, the algorithm fills the remaining slots using additional eligible PRs. It first selects additional PRs from applications already included in the sample whenever possible. If those are insufficient, PRs from new applications are added only as needed to reach the target sample size. This fill-up step ensures that the final sample reaches 25 PRs while continuing to control setup cost and application count.

Overall, this strategy produces a fixed-size sample that prioritizes coverage of accessibility issue types, maintains coverage of affected user demographics, includes at least 10 applications, and favors applications with lower setup risk. This approach is appropriate for our benchmark construction goal because the objective is not to estimate the population frequency of accessibility issues, but to create a manageable and well-covered set of real-world repair tasks for evaluating accessibility program repair.
