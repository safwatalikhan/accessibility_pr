Pull Request Sampling Strategy

From a manually curated dataset of 300 accessibility-related pull requests, we selected a sample of 50 PRs for detailed analysis and repair evaluation. Each PR in our dataset could be associated with multiple issue types and multiple affected user demographics, while each PR belonged to a single application. Because of this multi-label structure, simple random sampling is not suitable for our goal. A random sample could overrepresent frequent issue categories while missing less common but technically important accessibility problems. Therefore, we used a coverage-based sampling strategy that prioritized coverage across issue types and user demographics while controlling the number of applications included in the final sample.

Our primary sampling objective is to maximize issue type coverage so we can capture a broad range of accessibility repair tasks. Different accessibility issue types often require different repair actions, such as adding missing labels, correcting focus behavior, improving keyboard navigation, or adjusting visual presentation. Prioritizing issue type coverage helps ensure that the selected PRs represent a wide range of repair scenarios rather than many examples of the same kind of accessibility fix.

Our secondary objective is to maximize affected user demographic coverage. Accessibility issues can affect different groups of users, including users with visual impairments, users with motor impairments, users with cognitive impairments, and users who rely on assistive technologies. Since our study evaluates accessibility program repair, it is important that the sampled PRs reflect different user demographics. Therefore, after issue type coverage, we prioritize PRs that introduced previously uncovered user demographic labels.

Our third objective is to minimize the number of distinct applications required for evaluation, while preserving issue type and user demographic coverage. This decision is motivated by the practical cost of conducting repair experiments on real-world applications. Each additional application requires separate setup effort, including cloning the project, installing dependencies, configuring the build environment, reproducing the issue, applying generated patches, and validating the repair. Since our primary goal is to evaluate accessibility repair behavior across issue categories rather than application-level variation, we treated the number of applications as an experimental cost. This allows the sample to remain focused on issue and user coverage while reducing unnecessary setup overhead.

The sampling algorithm processes each eligible PR and extracts three fields: the set of issue types, the set of affected user demographics, and the application name. Since issue type and user demographic were multi-label fields, comma-separated values were split and normalized by removing extra whitespace. PRs with missing issue type or user demographic annotations are excluded from the sampling process because they could not reliably contribute to the coverage objectives.

During sampling, we maintain three sets representing the issue types, user demographics, and applications already included in the sample. For each candidate PR, we checked whether it introduced at least one previously uncovered issue type or user demographic. PRs that contributed new issue or user coverage were prioritized for selection. Application count is handled as a constraint: when multiple PRs could provide similar issue and user coverage, we preferred PRs from applications already represented in the sample. This reduced the number of distinct applications needed for evaluation without sacrificing the main coverage goals.

After the coverage-driven selection step, if the sample contained fewer than 50 PRs, we fill the remaining slots using additional eligible PRs from already selected applications whenever possible. This fill-up step ensures that the final sample reaches the target size of 50 while continuing to control the number of applications. If additional PRs from selected applications are insufficient, PRs from new applications are added only as needed to reach the target sample size.

Overall, this strategy produces a fixed-size sample that prioritizes coverage of accessibility issue types, maintained coverage of affected user demographics, and reduces the number of applications requiring experimental setup. This approach is appropriate for our benchmark construction goal because the objective is not to estimate the population frequency of accessibility issues, but to create a manageable and well-covered set of real-world repair tasks for evaluating accessibility program repair.
